정답: ④ (4번)

해설:
파일 업로드 취약점(위험한 형식의 파일 업로드, CWE-434)에 대한 근본 대책을 묻는 문항이다. 확장자 검사와 MIME 타입 검사는 모두 클라이언트가 조작할 수 있거나 우회(이중 확장자, 널바이트, 매직바이트 위조, 이미지 파일에 웹셸 삽입)가 가능하므로, 업로드된 파일이 웹 서버에서 스크립트로 해석되지 않도록 실행 경로 자체를 차단하는 것이 핵심이다.

각 보기 분석:
① 파일명 무작위 변경 — 경로 추측을 어렵게 하는 보조 대책일 뿐이다. 공격자가 업로드 응답이나 게시물 링크로 경로를 알아내면 그대로 실행되므로 근본 대책이 아니다.
② 업로드 파일 크기 제한 — 자원 고갈형 DoS 대응 수단이지 스크립트 실행 위험과는 무관하다.
③ 이미지 파일은 안전하다고 가정하고 웹 루트에 저장 — 가장 위험한 처리다. 이미지 헤더(매직바이트)를 정상으로 위장한 웹셸이 웹 루트에 저장되면 URL 호출만으로 서버 측 코드가 실행된다.
④ 실행 불가능한 별도 저장소에 두고 서버에서 직접 해석되지 않도록 분리 — 웹 루트 외부(또는 오브젝트 스토리지)에 저장하고, 다운로드는 별도 핸들러를 통해 제공하며 해당 디렉터리의 실행 권한과 스크립트 핸들러 매핑을 제거하는 방식이다. 확장자·MIME 검사 우회에 관계없이 코드 실행을 차단하는 근본 대책이다. 정답.

핵심 정리:
파일 업로드 방어 우선순위: 웹 루트 외부 저장과 실행 권한 제거 → 화이트리스트 확장자 검증 → 파일명 재생성 → 콘텐츠(매직바이트) 검사 → 크기 제한 → 백신 검사.
확장자·Content-Type(MIME)은 요청 값이므로 신뢰할 수 없다. 반드시 서버 측에서 재검증하되 이것만으로는 부족하다.
스토리지 분리 시 다운로드 응답에 Content-Disposition: attachment와 X-Content-Type-Options: nosniff를 함께 적용하면 브라우저 측 실행 위험도 줄일 수 있다.
