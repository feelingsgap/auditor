정답: ② (2번)

해설:
제시된 Java 코드는 request.getRawParameter("price")로 받은 원시 문자열을 아무런 검증 없이 Integer.parseInt()로 정수 변환한 뒤 total에 누적한다. 사용자 입력에 대한 형식·범위 검증이 전혀 없으므로 소프트웨어 개발보안 가이드의 "입력값 검증 및 표현" 분류에 해당하는 취약점이다.

이 코드에서 실제로 발생 가능한 문제:
숫자가 아닌 문자열 입력 시 NumberFormatException으로 예외 처리되지 않은 오류가 발생하고, 음수나 Integer.MAX_VALUE에 가까운 값이 들어오면 정수 오버플로(CWE-190)로 total이 비정상 값(음수 금액 등)이 되어 결제 금액 조작 같은 업무 로직 우회로 이어질 수 있다.

각 보기 분석:
① SQL Injection 여부 — 틀림. 코드에 SQL 질의문 생성이나 DB 호출이 전혀 없으므로 SQL Injection과는 무관하다.
② 입력값 검증 및 범위 체크 — 맞음. price에 대해 숫자 형식 검증, 최소·최대 범위 체크, 예외 처리가 모두 누락되어 부적절한 입력이 그대로 연산에 반영된다. 정답.
③ 위험한 형식의 파일 업로드 취약점 — 틀림. 파일 업로드나 저장 로직이 존재하지 않는다.
④ 디렉토리 경로 조작 — 틀림. 파일 경로 조합이나 파일 접근(File, FileInputStream 등)이 없으므로 경로 조작(Path Traversal)과 무관하다.

핵심 정리:
입력값을 바로 형변환·연산에 사용하는 코드는 "입력값 검증 및 표현" 취약점으로 분류한다. 대책은 화이트리스트 형식 검증, 상·하한 범위 체크, 예외 처리, 필요 시 BigInteger/long 사용이다.
parseInt 계열은 형식 오류 시 예외, 큰 값 누적 시 오버플로라는 두 가지 위험을 동시에 가진다.
취약점 유형 판별은 코드가 실제로 수행하는 동작(질의문 조합 / 파일 접근 / 경로 결합 / 단순 형변환)을 기준으로 판단해야 한다.
