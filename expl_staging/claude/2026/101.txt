정답: ② (2번)

해설:
SQL Injection 예방을 위한 시큐어 코딩 기법으로 권장되는 항목만 모두 고르는 문항이다. 행정안전부·KISA의 소프트웨어 개발보안 가이드에서 SQL Injection 대응의 핵심은 질의문과 데이터의 분리(Parameterized Query / PreparedStatement)이며, 입력값 검증은 이를 보완하는 방어 계층이다.

각 항목 판정:
ㄱ. Parameterized Query — 옳음. SQL 구문 틀을 먼저 컴파일하고 사용자 입력은 바인딩 변수(데이터)로만 전달하므로, 입력에 따옴표나 OR 1=1 같은 문자열이 들어와도 SQL 구문으로 해석되지 않는다. 가장 근본적이고 권장되는 대책이다.
ㄴ. Stored Procedure — 옳음. DB 내부에 미리 정의된 프로시저를 파라미터로 호출하면 질의문 조합이 발생하지 않아 SQL Injection 위험을 크게 줄일 수 있다. 다만 프로시저 내부에서 EXEC나 동적 SQL을 문자열로 조합하면 여전히 취약하므로 "파라미터로 처리하면"이라는 단서가 중요하다.
ㄷ. Dynamic SQL — 틀림. SQL 문을 문자열로 조합하여 실행하는 방식은 SQL Injection의 예방책이 아니라 대표적인 발생 원인이다. 예방 방법으로 제시된 것 자체가 오류다.
ㄹ. 입력값 검증 — 옳음. 형식·길이·범위·허용문자(화이트리스트) 검사를 통해 악성 입력의 유입을 차단하는 표준적인 보안 기법이다. 단독 방어로는 부족하지만 권장 기법에 해당한다.

각 보기 분석:
① ㄱ, ㄴ — ㄹ(입력값 검증)이 누락되었다.
② ㄱ, ㄴ, ㄹ — 옳은 항목만 정확히 포함하고 ㄷ을 배제했다. 정답.
③ ㄱ, ㄷ — 예방 기법이 아닌 ㄷ을 포함하여 오답이다.
④ ㄱ, ㄴ, ㄷ, ㄹ — ㄷ까지 포함하여 오답이다.

핵심 정리:
SQL Injection 1차 방어는 Parameterized Query(PreparedStatement)로 코드와 데이터를 분리하는 것이다.
Stored Procedure는 파라미터 바인딩으로 호출할 때만 안전하며, 내부에서 동적 SQL을 조합하면 여전히 취약하다.
Dynamic SQL(문자열 조합)은 대책이 아니라 취약점의 원인이다. 보기에 등장하면 오답으로 판단한다.
입력값 검증, 오류 메시지 최소화, DB 계정 최소권한은 심층방어(defense in depth) 보완 대책이다.
