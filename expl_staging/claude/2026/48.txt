정답: ② (2번)

해설:
지속적 통합(CI, Continuous Integration)에 대한 설명 중 올바르지 않은 것만 묶는 문항이다. CI의 핵심은 통합을 뒤로 미루지 않고 작은 단위로 자주(하루에도 여러 번) 수행하여 통합 지옥을 피하는 것이다.

각 항목 판정:
가. 지속적 통합은 특정 기능의 개발이 완료되었을 때 진행한다 — 틀렸다. 기능 완성 시점까지 기다렸다가 통합하는 것은 CI 이전의 빅뱅 통합 방식이다. CI는 커밋 단위로 수시로 통합한다.
나. 개발자가 저장소에 코드를 커밋할 때마다 진행된다 — 옳다. 커밋(또는 푸시)이 CI 파이프라인의 트리거가 된다.
다. Git이나 SVN 같은 버전 관리 도구를 사용한다 — 옳다. 단일 소스 저장소는 CI의 전제 조건이다.
라. 코드를 컴파일하고 통합하는 빌드 과정이 자동화된다 — 옳다. 빌드 자동화와 자동 테스트가 CI의 필수 요소이다.
마. 개발자는 코드 테스트를 완료한 후 커밋을 진행한다 — 틀렸다. CI에서는 커밋 이후 CI 서버가 자동으로 빌드하고 테스트를 수행해 통합 결함을 즉시 알려주는 것이 본질이다. 테스트 완료를 커밋의 선행 조건으로 두면 커밋 주기가 길어져 자주 통합한다는 CI의 원칙에 어긋난다.
따라서 잘못된 것은 가와 마이다.

각 보기 분석:
① 가, 나 — 가는 틀렸지만 나는 CI의 정확한 설명이므로 묶음이 성립하지 않는다.
② 가, 마 — 통합 시점을 기능 완료로 미룬다는 오류와, 테스트 완료를 커밋의 선행 조건으로 본 오류를 정확히 골랐다. 정답.
③ 나, 다, 라 — 세 항목 모두 CI의 올바른 설명이다.
④ 나, 다, 마 — 나와 다가 옳은 설명이므로 묶음이 성립하지 않는다.

핵심 정리:
CI의 3요소는 단일 소스 저장소(버전관리), 빌드 자동화, 자동화된 자체 테스트이며 커밋마다 파이프라인이 자동 실행된다.
"자주, 작게, 빠른 피드백"이 CI의 표어이므로 통합을 미루자는 취지의 서술은 모두 오답이다.
CI(통합·빌드·테스트 자동화) → CD(Continuous Delivery, 배포 가능한 상태 유지) → Continuous Deployment(운영 자동 배포)의 단계 구분도 함께 정리해 둔다.
